# Decisions log

Format: **what** · *why* · alternatives rejected. The log starts on 21 October 2026, the day the alignment of this dashboard with the other hub dashboards began (house style as in live-greekpower and Flows). Decisions marked *(existing)* were taken earlier, while the dashboard was built; they are written down here so that they are not lost.

| # | Decision | Why / what was rejected |
|---|---|---|
| D01 | This repository follows the **hub house style** (shell, loading overlay, language, accent, modal) while keeping its own analyses: RTE, arbitrage, avoided curtailment, surplus absorption, the CET / local-time alignment. It is handled in its own threads; documentation starts lean (`DECISIONS`, `KNOWN_ISSUES`, `ROADMAP`), with `ARCHITECTURE` / `DATA_DICTIONARY` / `METHODS` later | Same look and behaviour across the hub, one place to read why things are as they are. Follows live-greekpower D11 and D13 and Flows D01. |
| D02 | The accent colour is **emerald** (`#34d399`, with 200/300/500 tints), defined in one place at the top of `index.html` (`window.ACCENT`, used by Tailwind as `acc-*`). **Owner's decision, 21 Oct 2026: emerald stays the accent, and the greens that mean "complete / positive / ✓" become another green, lime** (`lime-400` / `lime-500`). In batch 1 the accent is used by the loading overlay (spinner, group icon, step bars) and lime by its ticks and the *ready* box; the rest of the page follows *(planned, K02)* | Emerald is the colour assigned to BESS in the hub (BigHydro D23: BESS emerald, Gas-Power blue, Flows cyan, BigHydro violet, live-greekpower platinum). Rejected: changing the BESS accent, since emerald is the identity of the page; and keeping one green for both, since decoration and "everything is fine" would then look the same. |
| D03 | **Loading overlay** paced as in live-greekpower D47 and Flows D03: all five steps visible from the start at half opacity; step 1 *Reading the data* follows the real download of the two files (`meta.json`, `historical.json`) with a 650 ms minimum; steps 2–5 are one per tab, in tab order (Daily Analytics, Monthly Impact, Surplus & Flexibility, Arbitrage P&L): each lights up, waits 20 ms, **draws its tab**, then its bar fills linearly in 350 ms and gets a ✓; *ready* stays 650 ms before a 0.5 s fade. Reduced-motion users get 120 / 200 / 200 ms. No percentage counter. If the data cannot be loaded the overlay stays, the spinner stops and a message asks the visitor to reload (same text as live) | Before, the data was loaded first and the overlay then played a timed animation with percentage counters that followed no real work. Same loading experience on every hub page. |
| D04 | English by default; the visitor's choice is stored in the browser under the shared key `kp_lang` and used on the next visit | Before, the page forced English at every load, so a visitor's choice was lost on reload. Follows live-greekpower D10: all dashboards share one origin, so the language follows the visitor across the hub. |
| D05 | The update runs **only** through the external **cron-job.org**, daily at **07:04 Athens time**; the workflow has no `schedule:` block. The cron-job.org job **already existed and worked before this alignment** (set up by the owner); this decision removes the two GitHub crons that ran next to it | The workflow still had its own schedule (05:00 and 05:30 UTC) in addition to the external call, so the fetch could be started more than once a day; GitHub's cron can be late; and a fixed UTC time moves in Athens time when the clocks change (08:00 → 07:00 after 25 Oct). cron-job.org runs in the Europe/Athens zone and keeps 07:04. Follows live-greekpower D02 and Flows D05. Rejected: keeping a GitHub cron as backup. |
| D06 | `data/meta.json` holds `fetched` (time of the run) and `next_update` (next 07:04 Athens, computed with the time zone, so correct across daylight-saving changes). Its only writer is `update_data.py`, after the data file was written successfully; the page shows both in Athens time and shows "–" if the file is missing | Before, the page took the latest data date and a fixed 08:00 as *Last update* and the next day 08:00 as *Next*, neither of which was the real run time. Python computes, the page only shows (live-greekpower D16). |
| D07 | Tailwind is pinned to 3.4.17 (play CDN) | The accent palette (D02) is passed through `tailwind.config`, an API of the 3.x play CDN; a pinned version stops a library release from changing the page overnight (live-greekpower D21). Chart.js is not pinned yet (K01). |
| D08 | GitHub Actions: `actions/checkout@v5`, `actions/setup-python@v6` (Python stays 3.11) | The earlier versions run on Node.js 20, which GitHub is retiring (live-greekpower D26). |
| D09 | **Header labels**: sentence case ("Last update:", "Τελευταία ενημέρωση:"); short labels on mobile ("Updated:" / "Next:", "Ενημέρωση:" / "Επόμενη:", hub-wide H02). Date and time are written in the visitor's language and in Athens time ("22 Oct, 07:04"), the same on desktop and mobile (no year) so that the mobile line fits on one row | Same labels as Flows; one format instead of two. |
| D10 | *(existing)* **Clock alignment**: market data (MCP, ISP) follow the CET market day, SCADA follows Greek local time (one hour ahead). With the ⏱ checkbox on (default), SCADA hour *h* is matched with MCP hour *h*−1 and the ISP follows the market clock; the checkbox appears in every card it affects and all copies stay in sync. Measured on 1 Jun–30 Sep 2026: ISP surplus hours against hours with MCP ≤ 5 €/MWh correlate best with no shift (0.773, against 0.746 and 0.711 one hour either way); pumping against price 0.505 with the one-hour shift (0.474 without), BESS charging 0.397 (0.363) | A statistical assumption, not IPTO documentation (K07). Its effect on the total June–September P&L is roughly 10%, which is why it is a switch. |
| D11 | *(existing)* **Avoided curtailment** counts only charging in hours where the (aligned) MCP is ≤ 5 €/MWh; charging at higher prices is arbitrage and is not counted. The threshold is one constant (`CURTAILMENT_PRICE_THRESHOLD`) | Curtailment of renewables happens when they saturate the market and the price falls to about zero; charging at 80 €/MWh cannot be avoided curtailment. |
| D12 | *(existing)* **Totals**: a unit's daily charge and discharge are the sums of its hourly values (quarter-hourly in the ISP); the SUM and TOTAL columns of IPTO's files are never added. **TOTAL BESS is the sum of the units** | IPTO's TOTAL row nets the units hour by hour and gives lower values; the physical charge and discharge of the fleet is the sum. Before, the SUM column was counted as an extra charge or discharge, which inflated the daily totals (908 of 1,108 unit-days did not match their hourly values) and gave impossible RTE values. |
| D13 | *(existing)* **ENTSO-E prices**: the API omits points whose price equals the previous one, so missing positions inside a period are filled forward to the end of the period; an hourly price is the mean of its four quarters; a day with a missing hour is not saved (the next run tries again); nothing missing is written as 0 | Before, omitted points were treated as gaps: hours at −0.01 €/MWh became 0 and some hours averaged only the quarters present (e.g. 32.92 instead of 16.46 on 18 Jun). |
| D14 | *(existing)* **IPTO files**: the sheet is chosen by its content (the one holding *TOTAL PUMPING* / *Energy Surplus*), never "the first sheet"; the metadata sheet `XDO_METADATA` is skipped | In files before 18 Jun the first sheet is the metadata sheet, so pumping before that date had been stored as 0. Re-running 1–17 Jun gave real values (e.g. 518 MWh on 11 Jun). |
| D15 | *(existing)* **Surplus absorption**: a surplus hour is an hour (aligned to Greek time) where the ISP residual is at least 1 MWh. BESS and pumping charging in those hours counts as absorption; charging outside them is shown apart in grey as arbitrage. The KPIs use only days with complete BESS, PUMP and ISP data; the red tile counts days when the residual exceeded what BESS and pumping absorbed in surplus hours (not a fixed GWh threshold) | Daily BESS charging barely changes with the size of the surplus (it behaves like a fixed-size sponge), so a share of the "theoretical surplus" mostly measures how big the surplus was. Monthly, energy-weighted figures in surplus hours do not have that flaw. |
| D16 | *(existing)* **Methodology** in two versions, *Short* (opens first) and *Detailed*, in both languages; the modal has a fixed title, a scrolling text and a fixed Close button; the page behind does not scroll while it is open; Esc closes it | A long text is not read on a phone. |
| D17 | *(existing)* **Hourly profile** (average day of the month, in Greek local time) is the first card of the Surplus & Flexibility tab, ahead of the daily and cumulative charts | It answers the question of the tab: does flexibility charge when the surplus is there? |
